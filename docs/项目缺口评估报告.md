# MediaCrawler 项目工程化与用户体验缺口评估报告

> 评估日期：2026-08-03
> 评估对象：`D:\WorkSpaceCoding\MediaCrawler`(NanmiCoder/MediaCrawler 的 fork，含自研 MCP 服务层与 Claude Code 插件)
> 评估方式：3 个并行代码探索代理全量扫描(核心爬虫层、MCP 服务层、工程化设施),交叉验证后汇总

---

## 一、总体结论

项目当前**不缺功能**——功能面已经相当完整:7 个平台、8 种存储目标、双转写后端、MCP 13 个工具、FastAPI + WebUI、Claude Code 插件市场。

真正的缺口集中在 **"从个人脚本演进成可靠服务"的中间态断层**:代码能跑、能用，但缺少让它"持续可靠地跑"和"让别人也能轻松跑起来"的工程地基。

---

## 二、工程化缺口(按严重度排序)

### 高危——直接影响"改代码敢不敢合并"

| # | 缺口 | 现状证据 | 影响 |
|---|------|---------|------|
| 1 | **没有任何跑代码的 CI** | `.github/workflows/` 里只有 `deploy.yml`,且只部署 VitePress 文档站 | fork 已领先上游 30 个提交,每次靠"本地跑一遍 pytest"保证质量,漏跑就带病进 main;上游合并也无门禁 |
| 2 | **日志不落盘、不轮转** | `tools/utils.py:31` 只有 `basicConfig`(控制台);`logs/` 里的文件全是 ps1 脚本手工重定向,无轮转策略 | 爬虫主程序崩溃后日志即丢失;`logs/` 无界膨胀 |
| 3 | **数据库 schema 无迁移工具** | alembic 已装(`pyproject.toml:12`)但全仓无 `alembic.ini`、无 `versions/`,靠 `create_all` + 手工维护 `schema_mysql.sql` | 改字段后老用户的已有表不会 ALTER,只能手工改库 |
| 4 | **lint 工具链残缺** | ruff 已装但 `pyproject.toml` 无 `[tool.ruff]` 配置;mypy 有 `mypy.ini` 但未装进依赖;pre-commit 不挂任何 linter | "lint 零警告"要求没有工具支撑 |

### 中危——影响长期维护成本

| # | 缺口 | 现状证据 |
|---|------|---------|
| 5 | **无版本发布体系** | 0 个 git tag、无 CHANGELOG、版本号双轨(`pyproject.toml` 是上游的 0.1.0,插件是 1.0.3,无关联无同步) |
| 6 | **无 Docker / 一键启动** | 主爬虫、API、WebUI、MCP 四个服务要手工开多个终端(README 自己写着"终端 1/终端 2");bat 脚本只覆盖 MCP server |
| 7 | **数据无清理策略** | `data/` 已达 **9.2GB**、`browser_data/` 899MB,无任何按时间/容量回收机制 |
| 8 | **无崩溃恢复** | 无全局 `excepthook`;无断点续爬(上游刻意留给 Pro 版,fork 可自行补齐);进程崩溃后从头开始 |
| 9 | **依赖双轨漂移** | `requirements.txt` 与 `pyproject.toml` 手工维护两份,已有不一致(aiosqlite 版本约束不同、requirements 缺 mcp/websockets/asyncpg 等);dev 依赖(pytest/pre-commit)混进生产依赖 |
| 10 | **配置管理两套风格** | 核心参数是硬编码模块常量不支持 env,只有 Whisper/数据库支持 env;无统一启动期校验(非法 `SAVE_DATA_OPTION` 要到运行时才在 7 个存储工厂里分别炸);数据库默认密码 `123456` 明文 |

### 低危——代码卫生

- 测试组织混乱:`test/`(上游 unittest)、`tests/`(fork 的 pytest,28 个文件)、`testse2e/`(空壳)三目录并存;无 pytest 配置文件;无覆盖率工具
- 101 处裸 `print` 与 logger 混用;131 处 `except Exception`;29 处 `import *`
- 7 个平台的 `core.py`/`login.py`/存储工厂高度同构复制粘贴(7×8≈56 个存储类),抽象层太薄
- 技术债残留:`init_loging_config` 拼写错误(`tools/utils.py:29`)、`ENABLE_GET_MEIDAS` 兼容别名(`config/base_config.py:153`)、`testse2e/__init__.py` 是 IDE 模板残留

## 三、用户体验缺口(站在"用 MCP 工具的人/LLM"视角)

MCP 层做得好的地方:错误统一返回 JSON、cookies 脱敏、`crawl_run_id` 运行目录隔离、登录失效 hint。明显短板如下:

| # | 缺口 | 现状 | 影响 |
|---|------|------|------|
| 1 | **爬取无进度反馈** ⭐最痛 | `crawl_*` 是同步阻塞调用,子进程跑几十分钟调用方只能干等;`crawler_runner.py` 的 `on_log` 回调已写好但 `server.py` 未接 | 用户/LLM 不知道任务是在爬还是卡死;2026-08-03 关闭硬超时后问题被放大——任务可无限挂起 |
| 2 | **返回值是 JSON 字符串而非结构化内容,体量不可控** | 所有工具返回 `str`;成功响应把 `data_summary` + `media_assets` + `transcription_jobs` + `log_tail` 全塞一起,无 fields/compact 参数;未使用 MCP 协议的 `isError` | LLM 上下文被大量消耗;客户端无法程序化区分失败 |
| 3 | **插件安装路径有断点** | 插件包被瘦身到只有 9 个文件,但 `.mcp.json` 指向 `127.0.0.1:8765`——通过 marketplace 安装后插件里没有爬虫代码,也不知道还要另行克隆仓库 + uv sync + 起 HTTP 服务 | 除作者外的人基本装不上;`plugin.json` 无 bootstrap 指引 |
| 4 | **转写任务重启后成孤儿** | `TranscriptionManager._tasks` 是内存字典,服务重启后 DB 里 running 状态的 job 永远卡死,无启动回收 | 重启服务后转写任务状态不可信 |
| 5 | **文档与实际不一致** | `docs/插件使用指南.md:15` 仍写"以 stdio 方式启动",`mcp-server-ops` skill 故障排查表还提 stdio 时代的 uv PATH | 排查问题时被误导 |
| 6 | **风控类失败无识别** | 登录失效检测只做"登录/login"子串匹配;验证码、滑块、IP 封禁(471/461)core 层只 log 不联动 | 失败归因不准,用户分不清是 cookie 过期还是被风控 |
| 7 | **无并发/任务管理** | 两个 `crawl_*` 并发调用会起两个浏览器进程,无队列、无互斥(只有单爬虫进程锁)、无任务列表/取消能力 | 多任务场景靠运气 |

## 四、投入产出比最高的前 5 件事

1. **给 MCP 爬取加进度反馈 / 异步任务化**——用户体验最痛,且刚关掉硬超时后完全没有兜底
2. **建一个跑 pytest + ruff 的 GitHub Actions CI**——已有 216 个测试函数,接 CI 几乎是白捡的安全网
3. **日志落盘 + 轮转**——半小时工作量,救每一次崩溃排查
4. **修复插件安装的"最后一公里"**——plugin.json 加 bootstrap 指引,或插件自带服务拉起能力;否则插件市场等于白搭
5. **数据目录清理策略**——`data/` 9.2GB 只会涨不会降
